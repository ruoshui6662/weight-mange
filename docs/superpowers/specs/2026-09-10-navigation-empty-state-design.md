# 导航交互与食物搜索空状态设计

## 问题定义

用户看到的每个可操作控件都必须产生可解释的结果。当前 Dashboard 底部导航按钮没有事件处理；本地食物目录为空时，搜索 API 返回空数组，但界面没有反馈，因此用户无法判断是“没有结果”“没有数据”还是“请求失败”。

## 第一性原理

1. **状态必须可观察**：用户触发动作后，界面必须显示当前页面、开发中状态、结果、空状态或错误状态之一。
2. **数据边界必须诚实**：搜索只读本地 active food catalog，不伪装成联网食品库；没有目录时应解释数据来源和下一步。
3. **M1 只交付饮食闭环**：体重和分析属于 M2，不在本轮虚构业务能力；但导航必须有明确反馈。
4. **已有业务能力优先复用**：不新增数据库表、不新增外部网络调用，沿用现有 API、CLI 导入和 session 边界。

## 范围

- 增加类型化的 Dashboard 导航状态。
- 实现“今日”“饮食”“我的”三个可用页面壳。
- 为“体重”“分析”提供明确的 M2 开发中状态。
- 为食物搜索增加加载、无结果和错误可见状态。
- 在空状态中提供本地目录导入说明，不增加浏览器上传接口。
- 补充单元/组件级回归测试，并更新进度记录。

## 非目标

- 体重记录、趋势分析或目标 CRUD 的新业务实现。
- 外部食品 API、联网兜底搜索或第三方数据授权。
- 数据库迁移、权限模型和容器部署变更。

## 验收标准

- 五个底部导航按钮均有动作：进入已实现页面，或显示明确的“后续开发中”状态。
- 搜索结果为空时显示本地目录说明和导入指引。
- 搜索请求失败时保留可读错误提示。
- 已有选择食物、份量和记账流程不回归。
- `pnpm test`、`pnpm lint`、`pnpm build`、`pnpm api:smoke`、`git diff --check` 全部通过。
