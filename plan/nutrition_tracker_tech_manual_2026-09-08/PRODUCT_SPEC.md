# PRODUCT_SPEC.md

## 1. 产品定义

本项目是一个**个人自用、自托管、Docker 化的饮食与体重管理系统**。它的核心不是“做一个卡路里计算器”，而是建立一条长期可靠的数据链：

> **食物识别 → 份量确认 → 营养计算 → 每日汇总 → 体重/运动记录 → 趋势分析 → 个人化能量估计 → AI 辅助解释。**

产品界面以薄荷健康的“浅灰背景 + 白色大圆角卡片 + 薄荷绿色强调 + 大字号数字 + 低信息噪声”作为主要视觉参考，但前端完全自行实现，适配手机与桌面。

项目仅用于个人自用，因此可以更自由地参考现有产品的页面布局和交互逻辑；仍建议不复制薄荷健康商标、Logo、专有插画和素材，以便后续代码可以自由维护、分享或重构。

## 2. 第一性原理

### 2.1 真正要解决的问题

饮食管理系统的目标不是精确知道“某一顿到底 437 还是 452 kcal”，而是：

1. 让每日记录成本低到足以长期坚持；
2. 让数据来源和计算路径可追溯；
3. 控制误差，不把未知值伪装成精确值；
4. 通过长期体重趋势反向校正个体能量消耗；
5. 把复杂营养信息转化成可理解、可执行的提示；
6. 即使 AI、外部 API、网络全部不可用，核心记录功能仍能使用。

### 2.2 系统的四个误差源

| 误差源 | 示例 | 系统策略 |
|---|---|---|
| 食物识别误差 | “馒头”到底是哪种馒头 | 本地食物库 + 别名 + 用户自定义 |
| 份量误差 | “一个”“一碗”“一勺” | household serving + 用户校准 |
| 营养数据误差 | 社区库、标签、数据库不一致 | source + quality + version + raw value |
| 能量消耗误差 | 公式 TDEE 与真实差异 | 先公式估计，后 Adaptive TDEE |

### 2.3 产品核心原则

- **Local-first**：核心数据默认只存于本地 Docker volume。
- **Offline-capable**：核心记录不依赖第三方 API。
- **Single-user-first**：第一版以单用户为目标，不为多租户牺牲简洁性。
- **Modular Monolith**：单进程/单容器优先，但代码按独立业务模块组织。
- **Schema-first**：数据库字段、API contract、营养计算接口先定义，再开发页面。
- **Snapshot History**：历史记录保存营养快照，不随食物数据库更新而漂移。
- **AI Never Owns Truth**：AI 只能解释、解析和提出候选项；营养数值由确定性引擎计算。
- **Graceful Degradation**：AI/OFF/USDA 不可用时，系统仍完整可用。

## 5. 用户核心流程

### 5.1 每日记录流程

```text
打开首页
  ↓
查看今日热量预算
  ↓
点击 +早餐 / +午餐 / +晚餐 / +加餐
  ↓
搜索食物
  ↓
选择份量或输入克数
  ↓
确定
  ↓
营养引擎生成 snapshot
  ↓
首页即时更新
```

目标：
- 常用食物：3 次点击内完成一次记录；
- 最近吃过的食物：2 次点击 + 数量确认；
- 复制昨日早餐：1 次确认；
- 页面首屏不要求滚动即可看到今日热量与宏量营养。

### 5.2 AI 自然语言录入

示例：

> 早餐吃了一个 75g 馒头、20g 燕麦、半个苹果、一个鸡蛋。

流程：

```text
文本
 ↓
AI Structured Extraction
 ↓
候选 Food Search
 ↓
生成候选记录
 ↓
用户确认/修改
 ↓
Nutrition Engine 计算
 ↓
写入日记
```

AI 返回的 kcal 不作为写入依据。

### 5.3 图片识别流程

```text
上传餐照
 ↓
AI Vision
 ↓
识别可能食物 + 大概份量
 ↓
显示候选列表
 ↓
用户校准重量
 ↓
搜索本地食物库
 ↓
确定性计算
```

必须清楚标注：
- “AI 估计”
- “重量待确认”
- “图片无法可靠判断食用油等隐性原料”

## 8. 关键功能验收标准

### 8.1 饮食记录

- 添加一条食物后，全天能量更新延迟 < 100ms（本地数据库场景）。
- 任何历史记录打开后，其 kcal 和宏量值与创建当时一致。
- 修改食物库中的营养值，不影响旧日记。
- 删除食物库条目，不导致历史记录丢失。
- “Tr”“—”“未知”不得全部强制变成 0。

### 8.2 数据导入

- 中国食物数据版本可以重复导入而不制造重复记录。
- 数据更新必须有 staging → validate → promote 三阶段。
- 导入异常不能破坏现有 food catalog。
- 每次导入保存 dataset version、checksum、日期、来源。
- 导入前后生成 diff：新增/修改/删除/异常。

### 8.3 AI

- AI 不可直接插入用户未确认的食物记录。
- AI 不能覆盖原始体重和饮食历史。
- AI 解析结果必须符合 JSON Schema。
- AI 请求失败不影响主应用。
- AI key 不输出到日志。
- API Key 可以通过环境变量覆盖数据库设置。

### 8.4 备份

一份完整备份至少包含：

```text
manifest.json
database.sqlite
uploads/
config-safe.json
```

不默认导出明文 AI API Key。

## 9. 成功指标

本项目是自用，因此不采用 DAU/转化率等商业指标，使用以下工程指标：

### 体验
- 手机端首页首屏 1 秒内可操作（局域网环境）。
- 最近食物搜索前 10 条结果 < 100ms。
- 食物记录 3 次交互内完成。
- PWA 全屏体验接近原生 App。

### 数据
- 导入 1677 条中国食物数据后可全部索引。
- 搜索支持中文名、别名、拼音首字母。
- 营养计算单元测试覆盖核心公式。
- 每次升级自动执行备份 + schema migration。

### 稳定性
- Docker 重启后数据完整。
- 无互联网时日记、体重、运动、统计正常。
- AI 服务故障不会影响基本功能。
- 数据库迁移失败时应用拒绝继续写入并保留原备份。

## 12. 非功能要求

- 单容器内存目标：空闲 < 300MB。
- 数据目录：统一 `/data`。
- 所有时间：数据库存 UTC + 本地 timezone setting。
- 所有主键：ULID/UUIDv7。
- DB 开启 WAL 模式。
- 外部 API 默认 timeout 10–30s。
- 上传图片自动压缩、限制尺寸。
- 日志采用结构化 JSON。
- 日志禁止记录 AI API Key、完整 Authorization。
- 可在局域网直接运行，也可放在 Caddy/Nginx 后。
- 默认不上传遥测。
