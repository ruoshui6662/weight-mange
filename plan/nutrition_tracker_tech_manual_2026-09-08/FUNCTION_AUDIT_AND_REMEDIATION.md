# 功能与操作逻辑审核及修改规划

审核任务：DOC-006。日期：2026-09-12（Asia/Shanghai）。源码基线：ae37b45。

## 1. 结论与边界

现有六页导航、日记快照、食物导入、菜谱计算、体重和分析模块的职责方向合理，但“接口已实现”“页面能展示”“用户能可靠完成任务”尚未完全对齐。建议先修复记录可靠性和日期语义，再补齐日常操作，之后继续运动/MET。无需推翻现有架构。

本报告是源码、产品规范及接口调用的静态审核，不是完整浏览器体验或安全审计。未对本次版本进行逐页截图、NAS 实测、数据库压力测试或故障注入；风险推导与缺失功能均在下面标明。既往测试数量不作为本次功能完整性的证明。本次只修改规划文档，不修复业务代码、不发布镜像。

第一性原理：用户必须能低成本记录事实、纠正错误、确认保存结果，并理解统计来自哪些记录。每个入口必须具有明确上下文、可观察结果和失败后的下一步。

## 2. 功能链路与职责映射

| 用户任务 | 当前入口与连接 | 合理性及应补齐的行为 |
|---|---|---|
| 初始化/登录 | App → auth status/session/bootstrap/login → profile/goals | 登录与已有会话恢复应进入同一加载流程；连接故障不能伪装成登录问题 |
| 查看今日 | TodayPage → dashboard + diary | 共用服务端事实源合理；刷新、跨日、返回页面必须重新校验日期和数据 |
| 添加食物 | 首页 FoodSearchCard / DiaryPage → foods/search → diary/{date}/entries → reload | 两套表单行为不一致；统一一个添加流程，入口只负责日期/餐次 |
| 修改/删除/复制 | 两页记录动作 → PATCH/DELETE/copy-day/copy-meal | 保留版本校验；补复制结果、冲突恢复和保存成功后的刷新异常区分 |
| 菜谱 | RecipePanel → recipes CRUD/refresh/add-to-diary | 原料快照和显式刷新方向合理；补草稿离开保护、提交结果不确定时的防重复验收 |
| 体重 | WeightPage → weights + weight-trend | 查询窗口、采样、原始值/趋势值需统一；补编辑删除入口 |
| 分析 | AnalyticsPage → overview + tdee | 只读估算合理；目前起终点图不等于完整趋势，限频不等于故障 |
| 我的 | ProfilePage → Setup → PATCH profile + POST goals | 首次设置被复用为编辑页，缺少回填、取消、当前目标和保存后资料刷新 |
| 备份与目录 | 我的说明 + 服务端能力 | 服务端能力不代表用户可操作；增加状态/说明入口，备份恢复留待专项安全验收 |

## 3. 已确认缺口与风险

P1：影响事实、写入可靠性或核心操作；P2：操作成本、理解和完整性问题。本次未证实灾难性数据丢失，不登记 P0。

### F01 / P1：已有会话恢复不加载今日数据

证据：`apps/web/src/App.tsx` 的首次 useEffect 获取 session/profile/goals 后只 setScreen；loadDashboard 只在显式登录、设置完成、写入等分支调用。DashboardView 的 effect 只加载体重/分析。

影响：刷新页面或重新打开已有会话时，dashboard/diary 初始 null 无人加载；页面可进入首页却显示数据不可用。这是代码路径缺口，需浏览器刷新用例复现。

修改：建立统一进入仪表盘流程，以当前 profile.timezone 显式计算日期；加载/失败/重试独立展示。401 才转登录，服务异常保持可重试状态。

### F02 / P1：调整目标未回填，保存后资料可能仍显示旧值

证据：App.tsx 的 Setup 初始化 height 为空、sex=none、activity=light、goalType=loss、calories=1800；ProfilePage 三个调整按钮都进入该表单；updateProfile 返回值未用于 setProfile。

影响：编辑身高可能顺带提交默认活动水平或目标；当前资料显示与持久化数据不一致。profile PATCH 成功而 goal POST 失败时存在部分成功。

修改：分开首次设置与编辑模式；回填当前资料和有效目标，提供取消；只提交明确修改的字段，保存成功更新 profile/goals；部分成功明确提示。目标生效日期沿用历史快照规则，禁止静默重写历史预算。

### F03 / P1：写入结果与刷新结果混用，重试存在重复记录风险

证据：App.tsx addEntry 在 POST 后清空选择再 await loadDashboard，二者共用 catch；saveEntry/removeEntry/copy 同样混合写入与读取。api.ts createDiaryEntry 每次调用生成新 idempotency-key。

影响：服务端成功但响应丢失，用户重试会用新 key；保存成功但读取失败时显示“请求未完成”，用户可能重复添加。此为代码推导风险，尚未故障注入复现。

修改：将状态拆为未提交、提交中、已保存待刷新、完成、结果待确认；同一次提交保留请求快照与 key，重试复用；已确认写入后只重试读取；保存中锁定冲突操作。审查菜谱加入、体重新增和复制动作同类风险。

### F04 / P1：日期体系与历史补录不完整

证据：DashboardView 使用 today 贯穿日记写入，没有独立 selectedDate；WeightPage 通过浏览器本地 `new Date(date + T12:00:00)` 转 UTC，服务端按用户时区生成 localDate；App 的日期随 render 计算，没有跨日刷新机制。

影响：不能直接查看/补录历史饮食；浏览器与资料时区相差很大时体重可能落到另一日期；长期开页可能使用旧日。

修改：today 与 selectedDate 分离，增加日期选择、回到今天、明确补录日期；统一用户时区转换；跨日/重新可见时更新 today，保留用户正在编辑的历史日期。

### F05 / P1：趋势时间窗口和数据完整性不一致

证据：WeightPage 使用 points.slice(-range)，实际截取记录数；TodayPage 筛选 today−7 至 today，但 App 请求 trend(7)；packages/body/src/index.ts 以最新记录日期及 windowDays−1 确定窗口。body listWeights 按时间升序 LIMIT；API 趋势调用 limit=500，因此超过 500 条时取最早记录。WeightTrendChart 按数组索引均分横轴。

影响：7 天可能实际展示跨度很长的 7 个观察点；一周前边界可能被截掉；长期使用后最新记录可能不进入趋势；缺失多日被画成等距相邻点。

修改：固定开始/结束日期并按真实日期映射横轴；首页保留用户要求的 today−7 至 today（含边界，共 8 个自然日），文案改为“一周前至今天”；体重页 7/30 日明确含今天的自然日窗口；后端按目标窗口查询，避免最早 LIMIT 截断。原始点与平滑线分别标注，单点不暗示变化，摘要说明比较基准。算法窗口/平滑初始化变化需要版本与专项回归。

### F06 / P2：M3-011 与已确认方案存在交付差距

证据：TodayPage 的搜索区始终位于卡片外下方；FoodSearchCard 没有 50/75/100g 快捷值、取消选择、来源质量详情；餐次无图标。总入口总是 breakfast。旧 DONE 证据覆盖按钮存在和聚焦，未覆盖全部承诺。

修改：抽出共享 FoodEntryComposer，在首页卡内按需展开；饮食页复用；四餐入口保留上下文，通用入口默认上次餐次并可显式切换；补快捷份量、取消与返回原入口焦点；保存成功滚回目标餐次。修正可访问名称与可见文字不一致的问题，导航测试使用 exact 查询。

### F07 / P1：编辑、搜索与错误恢复边界不足

证据：DiaryPage 数量输入没有 required，Number(空串) 为 0；App search 没有取消/请求序号，旧请求可能覆盖新搜索；errorText 大多合并为通用错误；冲突缺少“重新加载最新版本”动作。

修改：统一正有限数与精度校验；搜索仅接受最新请求结果；错误区贴近表单，区分输入、401、409、服务异常；保留草稿并提供重载冲突版本入口，不静默覆盖。

### F08 / P2：体重记录无法在页面纠错

证据：WeightPage 最近记录只读；api.ts 只暴露 get/create weight，而 body service 有 update/delete 与 version 校验。列表只显示前端排序后的 8 条，缺少完整历史入口。

修改：增加历史列表、编辑、删除确认、版本冲突恢复；保存后同步今日/体重/分析。先解决 F04/F05 再接入。

### F09 / P2：统计语义容易误解

证据：AnalyticsPage TrendSection 仅用 startKg/endKg 画一条线，斜率仅按涨跌方向选固定坐标；throttled 被标记“服务暂时不可用”并重试。TodayPage 热量装饰环为固定边框而非按进度绘制；本周概览仍为占位文字。

修改：起终点组件命名为“区间变化”或接真实时间序列；限频解释为“尚未到更新时间”，显示缓存/下次时间（接口不足时补 contract）；环形比例真实反映进度；百分比标“目标摄入比例”，不能鼓励超量冲到完成。没有真实数据的模块不显示示例数值。

### F10 / P2：食物库和设置的可用入口不足

证据：api.ts searchFoods 固定 limit=10，只取 payload.data，丢弃分页 metadata；前端未接食物详情、自定义、收藏/最近使用；ProfilePage 账户、时区和备份按钮因无 onAction 禁用，导入说明仍只介绍手动离线方式。

修改：增加分页/加载更多、来源与未知营养说明、自定义食物及最近使用；目录显示当前数量、导入状态和更新时间；只读设置用文本表示，避免无动作按钮；显示当前目标与生效日期。备份导出与恢复分开实施。

### F11 / P2：完成状态和测试覆盖不能代表产品完整度

证据：进度 M3 7/10 未计入 M3-011；Git 快照仍写未推送；README 的初始化/发布状态与历史实际工作不一致。M3-011 宣称完成却遗漏交互项；既有 E2E 主要是串行成功流程，缺刷新会话、写入响应丢失、跨时区、500+ 体重记录等场景。

修改：保留历史完成证据，追加验收差距，不重写历史；新任务覆盖遗漏项。任务表按稳定 ID 自动统计，明确“API 完成 / UI 接入 / 端到端验收 / 已发布”的区别；从新构建产物运行浏览器验收。

## 5. 验收与发布规则

每个任务先跑对应领域测试和故障场景，再按仓库门禁运行 lint/typecheck/test/build/api:smoke/test:e2e/diff check。涉及日期、快照、趋势、幂等和恢复必须有针对性证据，不能仅检查按钮文案存在。

浏览器矩阵：360/390/430/1024/1440；键盘完整路径、点击区、焦点返回、无横向溢出；正常/空/加载/失败/成功/冲突分别截图。长名称、大字体、无宏量目标也要覆盖。当前报告未完成该视觉矩阵，不能据此宣称视觉或无障碍通过。

端到端验收路径：
1. 初始化→设目标→退出→登录→刷新已有会话。
2. 从四餐分别添加→取消→快捷份量→保存→刷新→编辑→删除→复制。
3. 模拟服务器已写入但响应丢失，以及写入成功后汇总读取失败。
4. 历史补录→跨日→跨时区→返回今天。
5. 修改目标→检查当前资料→核对旧日预算不变。
6. 体重多点/稀疏/单点/500+ 条→图表→编辑删除→分析一致。
7. 备份→在隔离副本恢复→升级→重启→回滚验证。

每个任务独立提交，发布时将本地验收与 GHCR 构建成功分开记录；只在 NAS 拉取相应 digest 后确认线上版本。镜像构建成功不能替代 NAS 数据升级与实际操作验收。
