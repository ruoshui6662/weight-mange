# 全产品细节体验审核与优化方案（2026-09-13）

任务 ID：DOC-011  
角色视角：产品经理 / 用户体验审核  
审核对象：当前本地构建 `http://127.0.0.1:4173/`  
证据来源：Codex In-app Browser 当前运行截图、可访问性树、隔离 E2E 数据库与源码映射。  

## 1. 执行结论

当前产品已经具备可演示的基础闭环：用户可以完成登录、首次设置、搜索食物、按餐加入饮食、查看当日汇总、创建菜谱、记录体重、阅读分析并查看账户资料。界面已形成统一的 Data Garden 风格，信息层级和基础响应式明显优于早期版本。

但它还不适合被定义为“可信、顺手的日常记录工具”。最高风险来自数据而非装饰：实测输入 `2026-09-13` 的体重后，趋势显示为 `2026-09-14`，最近记录仍显示 0 条。其次是编辑目标会丢失已有身高且没有取消出口、低覆盖分析突出展示 `-1,577 kcal`、写入成功缺少统一反馈、部分主操作在常见桌面视口仍低于首屏。

产品优化顺序必须是：**先保证事实可信，再保证操作可恢复，然后缩短核心路径，最后统一视觉细节。** 在 M3-014 完成前，不建议把当前镜像作为稳定日常记录版对外承诺。

## 2. 第一性原理判断标准

1. **事实必须可信**：用户选择的日期、记录的数值和分析引用的数据必须一致；没有数据时明确缺失，不能用零值或推测替代。
2. **一页只有一个首要任务**：今日用于快速记录，饮食用于查阅与整理，菜谱用于复用组合，体重用于记录与趋势，分析用于理解证据，我的用于设置与数据管理。
3. **状态变化必须可感知、可恢复**：搜索、选择、保存、失败、重试、冲突和退出均需给出即时反馈，并保留用户输入。
4. **相同意图使用相同控件**：同样的“添加食物”“保存”“调整目标”应有一致的文案、流程、焦点与按钮层级。
5. **空状态必须指向下一步**：不能只解释“没有数据”，还要在当前上下文提供可执行动作。
6. **信息按决策价值排序**：高频动作和关键事实优先，方法说明、数据原则等低频解释后置或渐进披露。

## 4. 关键发现与解决方案

### P0 — 数据可信度

#### F01 体重业务日期发生跨时区偏移（M3-014）

- **证据**：在用户时区 `Asia/Shanghai` 下选择 `2026-09-13` 并保存 68.4 kg，趋势标签显示 `2026-09-14`，最近记录显示 0 条。
- **影响**：趋势、近期记录和分析统计引用了不同日期事实，用户无法相信数据。
- **方案**：把“用户选择的日历日”作为明确 API contract；服务端按资料时区生成时间戳，前端不得用浏览器时区拼接再 `toISOString()`。历史补录、跨午夜、东西跨日和夏令时纳入回归。
- **验收**：浏览器时区与资料时区不同时，输入日、列表日、图表日、分析日完全一致；同日更新不新增重复记录。

### P1 — 核心流程和决策安全

#### F02 目标编辑不是安全的编辑流程（M3-015）

- **证据**：“我的”显示身高 170 cm；点击“调整目标”后身高输入为空，页面只有“完成设置”，没有取消或返回。
- **影响**：用户无法判断保存会覆盖什么，误保存会丢失已有资料，放弃编辑也缺少显式出口。
- **方案**：新建与编辑使用不同页面状态；编辑态完整回填当前版本，显示“保存更改/取消”，脏数据离开时确认；每个设置分组只有一个明确入口。
- **验收**：打开即回填；取消不写入；保存后我的页与今日预算即时更新；历史快照不漂移。

#### F03 低覆盖分析呈现了过强结论（M3-020）

- **证据**：30 天中只有 1 天记录，页面仍把 `-1,577 kcal` 作为与平均摄入并列的大数字展示。
- **影响**：用户可能把单日差值误解为持续热量缺口，并据此调整饮食。
- **方案**：覆盖率未达到产品阈值时，将目标差值降级为“已记录日差值”，附 `1/30 天`；趋势性结论和建议保持锁定。把内部 `insufficient_data` 映射为人话和明确下一步。
- **验收**：低覆盖状态不出现无条件结论；事实、估算、建议在视觉和文案上可区分；页面不显示后端状态码。

#### F04 写入与搜索状态反馈不完整（M3-013、M3-017）

- **证据**：饮食写入成功只通过数值变化体现；搜索和选择后焦点退到页面根节点；份量没有快捷值，无结果缺少清空/改词动作。
- **影响**：用户会重复提交、键盘路径变长，弱网失败时也不清楚是否已保存。
- **方案**：建立统一异步状态模型：空闲、搜索中、已选择、保存中、保存成功、可重试失败；成功使用非阻塞 live region，失败保留输入和幂等键。选择后聚焦份量，提供 50/100/150/200g 和最近份量。
- **验收**：鼠标、键盘和读屏均能感知状态；重复点击只生成一条；失败后原食物、餐次、份量均保留。

#### F05 菜谱编辑器的提交动作不可持续可见（M3-022、M3-030）

- **证据**：1280×720 下保存/取消位于首屏以下；搜索结果选择后无明确播报；“添加原料”容易被理解成确认当前原料。
- **影响**：长菜谱编辑完成后用户不确定如何保存，新增行与选择食物的动作语义混在一起。
- **方案**：桌面使用底部 sticky action bar，移动端使用安全区固定提交条；将按钮改为“再添加一种原料”，食物结果动作改为“选用”，已选态展示可更换；保存前固定展示原料数、总重量和估算营养。
- **验收**：任意滚动位置都能看到保存状态；选择原料后焦点进入用量；未完成项在原地说明，不在提交后才报错。

### P2 — 信息架构、一致性和精修

#### F06 页面定向和导航状态不够明确（M3-028）

- **现状**：六页 H1 均为“你好，用户”；侧栏 hover 与 active 使用相同底色；全局顶部退出和“我的”危险操作重复。
- **方案**：H1 使用当前页面名，问候降为今日页副标题；active 增加左侧指示条或更强字重，hover 仅做轻微底色；退出只保留在“我的”，桌面页首使用头像/账户入口。
- **验收**：用户不看侧栏也能说出当前页面；hover 不会伪装当前页；高风险操作只出现于明确设置语境。

#### F07 今日页首屏和右侧辅助区价值失衡（M3-029）

- **现状**：热量卡和说明栏占用首屏，第一餐添加入口在本次真实浏览器视口仍低于可见区，与 M3-027 自动化验收存在环境差异。
- **方案**：桌面首屏优先展示热量摘要和至少两餐入口；将“数据说明”压缩为卡内信息按钮/Popover；热量卡主视觉保留，但减少重复副文案。
- **验收**：1280×720、1366×768、1440×900 三档带浏览器 UI 的视觉截图中，第一餐添加完整可见；不靠测试选择器或滚动偏移判断。

#### F08 空状态和操作文案缺少统一规则（M3-031）

- **现状**：菜谱空态只有页首“新建菜谱”，体重同时显示两个空态，按钮交替使用“添加/记录/新建/完成设置”。
- **方案**：所有空态采用“发生了什么 + 为什么 + 当前 CTA”；建立动词词典：饮食“添加食物”、体重“记录体重”、菜谱“新建菜谱”、设置“保存更改”。同一对象全站只用一个主动作名称。
- **验收**：六页空态均有就地动作；相同动作名称和层级一致；无重复空态或装饰性假数据。

## 5. 建议的信息架构

| 页面 | 用户的首要问题 | 页面主动作 | 次要动作 | 应后置的信息 |
|---|---|---|---|---|
| 今日 | 我今天吃了什么、还可吃多少？ | 对应餐次“添加食物” | 编辑/删除条目、复制昨日整天 | 数据口径说明 |
| 饮食 | 我想查阅或整理某天饮食 | 搜索并添加食物 | 切换日期、编辑记录 | 本地目录来源说明 |
| 菜谱 | 我想把常吃组合保存为可复用菜谱 | 新建菜谱 | 编辑、复制、加入饮食 | 快照与刷新机制 |
| 体重 | 我今天体重多少、趋势怎样？ | 记录体重 | 更正历史记录 | 趋势算法说明 |
| 分析 | 我的记录支持什么结论？ | 选择分析周期 | 前往补记录/调整目标 | 方法版本、置信度细节 |
| 我的 | 我想修改资料或管理数据 | 保存当前设置分组 | 导入、备份、退出 | 数据原则长说明 |

## 7. 推荐验收矩阵

| 维度 | 最小验收场景 |
|---|---|
| 数据正确性 | 用户时区与浏览器时区相同/相反；今天/昨天/历史日；同日更新；空数据不补零 |
| 核心路径 | 每餐添加、编辑、删除；菜谱新建/保存/取消；体重记录/纠错；目标编辑/取消 |

| 键盘/读屏 | 初始焦点、Tab 顺序、弹窗循环、关闭返回、live region、错误关联字段 |
| 桌面响应式 | 1280×720、1366×768、1440×900；首要动作不被浏览器 UI 挤出首屏 |
| 移动端 | 360×800、390×844、430×932；软键盘、底部安全区、单手触控、无横向溢出 |
| 文案一致性 | 同对象同动词；不暴露内部字段/状态码；事实、估算、建议分别标识 |

## 8. 证据限制
