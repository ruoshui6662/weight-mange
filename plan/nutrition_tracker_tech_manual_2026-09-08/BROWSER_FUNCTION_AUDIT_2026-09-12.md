# 浏览器功能与操作体验审核（2026-09-12）

## 1. 结论

核心链路可以运行：首次设置、会话恢复、食物搜索、分餐添加、记录编辑、菜谱创建、体重录入、分析读取和六页导航均能完成。当前版本不应按“完全可用”验收，因为浏览器实测确认两项会造成用户误判的数据错误：有饮食记录时餐次仍显示“暂无数据”，以及浏览器时区与用户时区不一致时体重会落到次日。

本轮没有修改业务代码。原因是修正跨越 Dashboard contract、日期 contract 和多个交互状态；按任务独立执行，先冻结证据与设计，再逐项 TDD 实施。

## 2. 测试边界与环境

- 浏览器：Codex 内置浏览器，桌面 `1440 × 900`、移动端 `390 × 844`。
- 服务：仓库自带 `scripts/e2e-server.mjs`，使用隔离临时 SQLite 数据库。
- 用户时区：`Asia/Shanghai`；浏览器运行时区：`America/Los_Angeles`，用于验证跨时区日期。
- 食物目录：隔离环境只预置“馒头”，不代表飞牛环境远程食物目录的完整性。
- 数据：创建 1800 kcal 目标，午餐加入 150 g 馒头后编辑为 120 g；创建测试菜谱；记录 70.5 kg 体重。
- 删除动作未执行：浏览器自动化对删除必须逐次确认。本轮已验证删除入口存在，未验证确认后的服务端删除结果。
- 浏览器控制台：操作结束后未发现 error 或 warning。

## 4. 可用、不可用与习惯偏差

### 4.1 当前可正常使用

- 首次设置、登录会话恢复和退出。
- 六个主导航切换。
- 今日热量总摄入与剩余热量。
- 本地食物搜索、选择餐次与克数、加入和编辑记录。
- 菜谱创建、原料选择和总营养计算。
- 体重写入接口本身、分析读取、桌面和移动端无横向溢出。

### 4.2 当前不可依赖

- 餐次热量：记录存在时仍可能显示“暂无数据”，不能用于判断哪餐吃了多少。
- 体重所属日期：跨时区环境会偏移一天，连带近期列表、趋势和分析缺失。

### 4.3 不符合用户习惯

- 保存成功后缺少即时确认和回到结果位置；用户容易重复点击或怀疑失败。
- 空关键词搜索无反馈；无结果虽有解释，但连续记录仍需反复搜索。
- 资料编辑复用首次设置页，却不回填、不允许取消，也没有明确“正在编辑”语义。
- 菜谱使用内部营养字段名，且先允许执行必然失败的“加入日记”。
- 移动端添加链路从餐次卡跳到长页面下方，目标餐次、搜索、份量和结果不在同一操作上下文。
- 分析页把内部 reason token 暴露给用户。

## 5. 已确认根因

### F01 — 餐次汇总 contract 不一致（P0，M3-021）

- 服务端 Dashboard 直接把 Diary 的 `mealTotals[slot.key]` 透传出去。
- Diary 的真实结构是 `totals.nutrients.energy_kcal.amount`。
- Web 类型和页面却声明并读取 `totals.kcal`。
- 结果是全天汇总能从另一字段正确显示，但每餐 `kcal` 为 `undefined`，UI 将其解释为“暂无数据”。

相关位置：

- `packages/dashboard/src/index.ts`
- `packages/diary/src/index.ts`
- `apps/web/src/api.ts`
- `apps/web/src/ui/TodayPage.tsx`
- `apps/web/src/ui/DiaryPage.tsx`

推荐设计：Dashboard 在服务边界生成稳定的页面模型 `totals: { kcal }`，不让前端理解营养引擎内部快照结构；同步前端类型，并增加真实 API 形状的集成测试和浏览器回归。这样修复范围小，同时避免未来 Diary 内部结构再次泄漏到 UI。

### F02 — 体重日期使用浏览器时区构造时间（P0，M3-014）

- 体重页把日期字符串拼为浏览器本地中午，再调用 `toISOString()`。
- 服务端随后按资料时区重新计算 `localDate`。
- 当浏览器位于洛杉矶、资料时区为上海时，中午换算后已是上海次日。

相关位置：`apps/web/src/ui/WeightPage.tsx` 及体重写入 API contract。

推荐设计：用户选择的是“资料时区中的日历日”，应由共享日期工具按资料时区生成稳定时间点，或让 API 明确接收 `localDate` 并在服务端建立时间戳。禁止由浏览器机器时区解释业务日期，并覆盖东西跨日、夏令时和历史补录测试。

## 7. 首个任务的验收设计

M3-021 采用服务端适配方案：

1. 先写 Dashboard 单元/集成 RED 测试，输入 Diary 的真实 nutrient snapshot，断言输出 `meal.totals.kcal`。
2. 同步 Web API 类型，移除与真实响应不一致的手写假结构。
3. 首页与饮食页继续消费相同页面模型，不做重复营养计算。
4. 浏览器回归覆盖空日、单餐、有多餐三种状态，并断言餐次之和与全天总量一致。
5. 运行 focused tests、全量 lint/typecheck/test/build/API smoke/E2E 和 `git diff --check` 后才标记 DONE。
